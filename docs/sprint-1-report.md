# Sprint 1 レポート

## 1. 提供されたベースライン (Delivered Baseline)
Sprint 1では、新規インベーダーゲームの最小限かつ検証可能な垂直スライス（Vertical Slice）を実装しました。主な成果物は以下の通りです。

- **Go HTTPサーバー**: 外部依存なしで動作する軽量なWebサーバー。ヘルスチェックエンドポイント (`/health`) と静的アセット配信機能を実装。
- **フロントエンドスライス**: ゲームタイトル画面と基本操作説明を表示する静的HTML/CSS/JS。プレースホルダーではなく、主要ユーザーパス（ゲーム開始〜初期画面遷移）が検証可能な状態。
- **インフラストラクチャ**: Dockerfile、Helmチャート（Deployment、Service、リソースデフォルト、プローブ設定）、GitHub Actions CIワークフロー（ビルド、テスト、lint）。
- **ドキュメント**: README（製品コンセプト、ユーザー体験、受け入れ基準、ローカル実行手順）。

## 2. QA証拠 (QA Evidence)
以下の検証コマンドを実行し、すべてパスしました。

- `go build ./...` および `go test ./...`: コンパイルエラーなし、ユニットテスト通過。
- `docker build -t invader-game .`: イメージビルド成功。
- `helm template .`: マニフェスト生成成功、ラベルとセレクターの一貫性確認。
- `curl http://localhost:8080/health`: 200 OK 応答確認。
- ブラウザによるUIレンダリング確認: タイトル画面と操作説明が正しく表示され、製品名とコンセプトが一致していることを確認。

## 3. 実施した修正・リメディエーション (Remediation Performed)
- **コンセプトの一貫性確保**: 初期スキャフォールディング段階で生じかねた「複数の製品名」や「矛盾した差別化要素」を排除し、単一の製品コンセプトをREADME、コード、UIラベル全体で統一。
- **静的アセットの接続確認**: Goサーバーのルートハンドラーがプレースホルダーテキストを返す状態を修正し、実際のフロントエンドUIが配信されるようにルーティングを調整。
- **CIパイプラインの安定化**: 依存関係の明示的なロックと、lint/テストステップの順序最適化により、fresh checkoutからの再現性を確保。
